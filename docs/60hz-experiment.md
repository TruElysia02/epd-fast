# 60Hz 扫描与 60FPS 内容实验

实验日期：2026-10-29。硬件沿用同一块 XIAO ESP32-C6 与 T94 配置的 2.9 寸屏；SPI 保持 20MHz，没有提高驱动电压或修改 VCOM。

本次分开验证三个问题：控制器每秒完成多少次短扫描、视频每秒推进多少个目标帧，以及实屏轮廓、对比度和残影表现。串口扫描统计与解码校验只覆盖前两项的一部分，不能证明光学响应达到 60FPS。

## 频率档位是主要突破

原来的完整 RAM 上传动画约 38.5Hz，其中一次 BUSY 约 20ms。仅把 SPI 传输或 CPU 计算优化到零，也无法在 16.67ms 内完成原来的扫描。

当前单扫描波形只执行第 1 组 A 阶段。依据 [SSD1680 Rev 0.14，p14–15](https://files.seeedstudio.com/wiki/Other_Display/213-epaper/IC%20Driver%20SSD1680%20Datasheet.pdf#page=15) 的波形映射，只修改 LUT 数组下标 144（从 0 计数）的低 3 位，也就是该组的 `FR`（扫描频率选择器）。波形方向、保持状态和电压参数不变。`fr N` 的数字是档位代码，不是 Hz，也不是线性比例。

全部 296 行、全零保持掩码、每档 32 次扫描的平均 BUSY：

| 档位 | BUSY |
| --- | ---: |
| 0 | 66.744ms |
| 1 | 40.047ms |
| 2，原始默认 | 20.013ms |
| 3 | 13.356ms |
| 4 | 10.030ms |
| 5 | 8.017ms |
| 6 | 6.688ms |
| 7 | 5.740ms |

这些是当前实物上的测量，不是所有 SSD1680 面板通用的时间表。空保持扫描验证了控制器时序，显示质量还要用运动图案和静态参考区确认。

原始采样见 [频率档位日志](../measurements/60hz-frequency-sweep.json)。

频率升高会缩短每个脉冲的作用时间。同样的 7 次预算，在档位 2 和 7 下的累计驱动时间不同；不能因为扫描率提高，就声称对比度、残影或应力保持等价。脉冲差模型也不直接测量粒子位置或电荷。

## 20FPS 素材上的传输与等待优化

使用原有 20FPS 视频的前 12 秒，各组保持档位 7、黑白预算 7/7、不限速、20MHz SPI。下面每行在上一行基础上增加一项改动；剔除第一段包含启动过程的统计，对后续 5 个约 2 秒活动区间取平均。

| 配置 | 扫描率均值 | 平均上传耗时 |
| --- | ---: | ---: |
| 全屏上传、轮询等待 | 78.87Hz | 4268.6μs |
| 加局部行上传 | 99.10Hz | 1685.6μs |
| 加 BUSY 下降沿唤醒 | 104.99Hz | — |
| 加相同掩码平面复用 | 119.66Hz | 537.8μs |
| 再裁剪实际 gate 至 63…233 | 119.55Hz | — |

局部行上传覆盖当前和上次非零掩码范围的并集，保证移走的旧驱动掩码被清除。平面复用仅跳过与最后成功写入 RAM 的内容相同的平面；每次复位或重新准备后的首扫仍完整写入两张 RAM，失败会使缓存失效。BUSY 为高时不会发送新命令。

**表内 119.66Hz 仍是在 20FPS 素材上获得的活动扫描率，不是已完成 119.66FPS 内容播放的证据。** 同一个目标帧可能跨多次扫描继续消耗预算。第一段统计、清屏停顿以及无变化场景不应混入这组活动区间均值，也不能据此代表整片平均帧率。

原始采样见 [20FPS 素材对照日志](../measurements/60hz-20fps-comparison.json)。

## gate 裁剪没有兑现此前的比例估算

离线解码旧视频的全部 4641 帧，发现内容仅占原生行 63…233，其他行始终是黑边。此前按行数比例推测只扫描这 171 行能缩短忙时。

实际在档位 2 下，只改 gate 范围后 BUSY 仍约 **20.014ms**；在档位 7 的累加对照中也未获得扫描率提升。因此本次不将 gate 裁剪作为默认优化，不再使用按 171/296 推导出的帧率估计。这个结果仅说明本次设置中的时序没有受益，并不证明所有局部 gate 配置都无效。

`scan FIRST LAST` 改变实际 gate 配置，`window partial` 改变 RAM 传输范围，两者不同。为避免软件记录未真正施加的驱动，所选 gate 范围之外若出现非零掩码，固件会明确报错；切回方块、细线、反向或时钟画面时恢复全屏 gate。

## 60FPS 内容与验证范围

后续使用已有的本地 29.97FPS 原片，先缩放，再用 FFmpeg 运动补帧生成 **13920 帧、60 个目标帧/秒、232 秒**的视频。它是估计中间运动的派生内容，不是下载得到的原生 60FPS 片源。补帧时发现 47 帧在原黑边区域出现少量溢出像素；转换时显式恢复原生行 63…233 之外的黑边，不改变内容区。

对第 10 秒附近的 2 秒片段抽查：120 帧中的 119 对相邻帧均不相同，检查的 59 个间隔帧也都不同于两侧帧。这支持该片段生成了新的中间图像，不是单纯复制帧；它不代表全片每一帧都不同。命令、抽样和素材校验值见 [素材处理记录](../measurements/60fps-source-processing.json)。

RLE 数据改为每帧一个带校验的 zlib 数据流后，完整素材为 **3,474,244 字节**，可与应用一起放入当前单应用分区。设备使用 ESP32-C6 ROM 解压器，桌面测试使用仓库中保留许可的 miniz 解压代码。格式、生成命令与逐帧校验方法见 [视频说明](../assets/README.md)。

桌面测试已逐帧核对这组素材；设备停机时抽查的 11 个边界和随机帧，其校验值也与桌面结果一致。随机跳转需要从关键帧重建，最长一次约 49ms；顺序单帧解码约 0.8…1ms，两者用途不同，不能把随机跳转耗时当作每帧持续播放的成本。

使用完整 296 行 gate、局部 RAM 上传、平面复用和下降沿唤醒，对档位 4、5、7 各播放前 16 秒。档位 7 中间 6 个统计区间的扫描率为 **101.99…115.17Hz**，接受内容索引的速率为 **59.70…60.46Hz**，这些区间均未跳过索引。末段为 57.86Hz、跳过 2 个索引，存在复杂场景和收尾统计混合的影响；档位 4、5 的后段遗漏更多。因此短测支持“多数活动区间及时推进约 60 个目标帧/秒”，不支持“整片始终零漏帧”的结论。[60FPS 素材短测日志](../measurements/60hz-60fps-short-tests.json)

`MEASURE` 指标的含义：

| 指标 | 统计内容 |
| --- | --- |
| `scan_hz` | 实际完成的控制器短扫描，包含驱动和保持扫描 |
| `content_hz` | 软件接受过的不同视频帧索引/秒；连续索引即使位图相同、无需扫描也会计数 |
| `skipped` | 当前统计区间跳过的视频索引数 |
| `render_us` | 目标图生成/解码路径的平均耗时，不是独立的纯解压基准 |

`content_hz` 不是每秒不同画面的数量，也不是光学转色率。

完整 232 秒的档位 7 基准已在设备日志中到达 `APPLE end`，随后报告完成收尾并关闭升压。110 个 `MEASURE` 区间的 `content_hz` 算术均值为 **59.94Hz**，中位数 59.96Hz，范围 **58.36…60.49Hz**；区间内 `skipped` 合计 11。期间有启动全刷和 11 次定期全刷，视频时钟在全刷时暂停；这些区间统计排除全刷停顿，不能当作包含停顿的整片墙钟平均帧率。[完整播放日志](../measurements/60hz-full-playback.json)

监控脚本在片尾等待自动状态行时超时，原始 `completed_first_pass=false` 和 `loop_started=false` 标记保留，没有改写成成功。设备正文包含片尾与收尾关电事件，后续显式 `status` 又确认 `running=0`、`fault=0`、`analog=0`；这组补充观察单列在日志的 `observations` 中。因此可以确认设备播到了片尾并停机，但不能说本次自动监控流程完整通过，也没有凭此证明循环已经重新开始。随后固件缩短状态行并主动发送完串口输出，没有改动视频推进逻辑。

实屏用户对档位 7、7/7 脉冲预算的反馈为：“更流畅，能看出是60Hz，残影严重不少”。因此最快档位 7 的结果只支持吞吐和内容推进能力，**没有通过光学显示质量验证**；不能把表中各项都称为已可长期使用的优化。

随后将档位降至 5，保持 7/7 预算及其他传输优化，用户反馈：“残影减轻了，但还是有，还有优化空间吗”。这说明当前实物上流畅度与残影存在取舍，档位 5 也不是已经消除残影的最终方案。[档位 5、7/7 实机记录](../measurements/60hz-fr5-quality-trial.json)

继续保持档位 5，对黑/白脉冲预算做了以下实屏对照：

| 黑/白预算 | 用户观察或选择 |
| --- | --- |
| 11/11 | “略有改善”，仍未确认消除残影 |
| 7/11 | 与 11/11 对比后，用户表示“11/11更好” |
| 11/7 | 用户要求“再来一次11/11”，尚未明确评价 11/7 本身的优劣 |

日志分别见 [11/11 对照](../measurements/60hz-fr5-budget11-trial.json)、[7/11 对照](../measurements/60hz-fr5-budget7-11-trial.json)、[11/7 对照](../measurements/60hz-fr5-budget11-7-trial.json)。不能仅根据要求重播，就推断 11/7 比其他设置更好或更差。

按用户要求，本轮最后恢复以下运行参数，让设备继续整片循环，保持配置供其观察：

| 项目 | 当前运行值 |
| --- | --- |
| 波形频率档位 | 5 |
| 黑/白脉冲预算 | 11/11 |
| 实际 gate 扫描 | 全部 296 行 |
| RAM 上传 | 当前与上次活动行的并集 |
| 相同掩码平面复用 | 开启 |
| BUSY 等待 | 下降沿唤醒 |
| 全刷后额外诊断等待 | 0ms，仍执行复位与重新准备 |
| 扫描限速 | `fps 0`，不限速 |
| 内容与播放方式 | 60FPS 补帧素材，整片循环 |

这是目前的观察配置，不是已确定的最优参数，也不是彻底去残影的结论。固件的保守默认值没有因此改变。

取消额外诊断等待的 `guard 0` 短测已通过。标准全刷和重新准备约 **1.75 秒**，相比保留 3000ms 等待时约 4.75 秒；硬件复位步骤仍保留。

## 继续减少残影的试验

增加了一个离线内容选项和四个可独立切换的运行选项，默认均关闭：

| 选项 | 含义与代价 |
| --- | --- |
| `--temporal-filter confirm2` | 预读一帧，逐像素过滤仅持续一帧的翻转；帧数和时间轴不变，但会删掉短促细节 |
| `pipeline on` | 在 BUSY 期间复制规划器，预测当前成功后的状态并预览下一目标；成功才交接，额外占用约 133KB RAM |
| `history 100/150/200` | 用位置估计调整未完成反向的返回剂量；不是实测光学位置，需实屏校准 |
| `paired on` | 在一个驱动阶段后追加一帧 HOLD；每次 activation 仍只算一次驱动，但忙时增加 |
| `weak 1` … `weak 4` | 黑色尾部使用 VSH2；两次弱态记作一次强态仅为实验假设，比例未标定；最轻一档视频试验未获益 |

过滤后全片仅有约 0.0476% 的像素时间样本改变，总转向减少 10.76%，四帧内的快速反向减少 36.46%。原始和过滤后均为 13920 帧、60FPS、232 秒，首末帧保持一致。用户反馈为“感觉减轻了，但感觉又差别不明显”，尚不能判定明显改善光学残影。[离线统计](../measurements/60hz-temporal-filter.json)

在相同过滤素材、FR5、11/11、局部上传、掩码复用和 IRQ 等待下，重播前 16 秒，去掉第一个启动统计区间，后续六段活动扫描率均值由 **83.13Hz 提高到 97.56Hz**，约提高 **17.4%**。对应内容索引接受率均值由 59.83Hz 提高到 60.01Hz，六段跳过索引合计由 2 降至 0。影子状态每次复制约 538…539μs，其复制、提交预测和预览工作大部分藏在 BUSY 中；这些 CPU 时间不能再全部加在扫描忙时之后。用户对开流水线的实屏反馈是“残影或对比有改善”。[实机短测](../measurements/60hz-followup-trials.json)

历史模型复用原有逐像素预算字节保存估计位置，没有再增加逐像素数组。位置范围为 0…LCM(B,W)，每方向步长为 LCM/B 或 LCM/W，完整转色仍恰好 B/W 次。只有未完成方向发生反转时，才按 100%、150%、200% 重估到新目标的距离；多次反向保留上次达到的位置。LCM 超过 255 的预算组合在开启此选项时明确拒绝，关闭时仍支持全部 1…32 预算。预览、重复规划和采用预览均不改估计位置，成功扫描的提交才更新位置及真实脉冲计数。100% 试验得到“残影或对比变差”的反馈，未保留为推荐配置。

`weakprobe N` 是独立、限次的源状态探针：在白底和黑底上按 HOLD、A、weak、B 四列比较 `00/10/11/01` 状态，仅将未用的 `11` 状态映射到已配置的 VSH2，没有增加电压。探针不经过预算模型，结束补一轮 HOLD 并关升压；恢复动画会重新全刷和初始化模型。弱态的光学方向及剂量尚需观察，不能直接当作已校准的弱收尾。

11 次探针的用户观察为“好像没看出区别”，无法据此区分弱剂量不可见和源状态映射问题。又增加了 `weakprobe N sameA` / `sameB` 对照：让 `11` 分别选择与 A、B 完全相同的现有电平，保持电压寄存器不变。放大的方块用 4 次脉冲作比较；sameA 中用户描述斑驳密度略有差异，但仍难以判断，未由此认定映射一致或错误。

随后只比较上排原为白底的 A 与 weak 框内区域，用户明确观察到“weak 明显更浅”。它支持该选态的驱动效果较弱，但没有量出实际剂量比例。按实验假设将黑向最后一次强扫描替换为两次弱扫描（`weak 1`），白向保持 11 次强扫描，仍使用 FR5 和流水线。用户反馈“变淡或残影变差”，因此恢复 `weak off`，没有再增加弱尾比例。软件半单位模型、掩码及流水线一致性测试通过，不代表“弱态等于半强”得到光学校准。

150% 的用户反馈为“差别不明显或仍变差”，200% 的对照选择为“固定 11/11 更好”。因此三档历史模型均未胜过固定预算，恢复 `history off`。此结果不能推广成所有历史模型都无效，只说明当前线性位置估计和这三组系数未改善本块屏幕的表现。

追加 HOLD 在 FR7 下将 BUSY 增至约 **11.47ms**，活动扫描约 70…75Hz。11/11 的反馈为“变差不少”；将预算增至 15/15，使累计有效驱动时长接近 FR5 的 11/11 后，反馈仍为“还是很差的感觉，全屏的残影”。因此也恢复 `paired off`，回到 FR5、11/11、流水线开启、历史补偿关闭。不能仅凭累计驱动时长相近，就认为像素的动态响应相同。

最终保留的观察配置为：过滤后的 60FPS 素材、FR5、11/11、流水线开启、局部上传、掩码复用、IRQ 等待、guard 0；历史补偿、追加 HOLD、弱收尾均关闭。残影仍存在。固件启动默认值保持保守，以上配置需要显式设置。

最终配置又完成了 260 秒监控：232 秒内容到达片尾并自动开始下一轮，监控结束时仍为 `running=1`、`fault=0`、`video_loop=1`。第一轮片尾前记录到 11 次全刷与准备（含启动、10 次定期全刷）。111 个打印统计窗口的内容索引接受率均值约 **59.96Hz**，范围 58.82…60.49Hz，窗口内 `skipped` 合计 10。全刷会重置未满的统计窗口，因此合计不代表整片精准漏帧数；均值也排除全刷停顿，并非墙钟平均或光学转色率。设备上第 0、1234、13919 帧校验值均与过滤后素材一致；2 秒短片还观察到两次自动循环重启。[最终循环及 ROM 校验](../measurements/60hz-pipeline-loop-validation.json)

## 默认设置与复现实验

固件默认仍为波形档位 2、完整 RAM 上传、不复用掩码、轮询等待、全屏 gate、目标 30Hz、额外诊断等待 3000ms。上电显示全刷参考图并停止；循环播放需发送 `apple loop`。

档位 7 的传输实验配置可在串口依次设置，每条停止型配置命令完成后再发送下一条：

```text
fr 7
scan full
window partial
reuse on
wait irq
apple 12
```

`apple` 命令本身选择不限速扫描。`fps N` 只限制扫描调度，不改变已经编码的视频内容帧率。`guard 0` 可取消标准全刷后的额外诊断等待，硬件复位与重新配置仍保留；默认等待为 3000ms。

每 45 秒或 2000 次扫描仍会标准全刷。高速下通常先触发扫描次数上限，视频时钟在全刷时暂停；清屏停顿需单独报告。`settle` 取消循环、完成当前目标并关闭升压，`stop` 取消循环并全刷停机。`verify N` 只允许在停机状态对第 N 帧解码并输出 FNV-1a 校验值；校验一致只能证明数字图像一致，不能证明面板已经完成转色。
