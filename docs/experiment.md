# XIAO ESP32-C6 + 2.9 寸 T94 黑白高刷验证

> 这是迁入仓库前的实验记录，v1–v6 是当时的迭代编号。当前构建入口与可选视频步骤以根目录 README.md 为准。

这是独立的实验固件（v6，含 Bad Apple 播放），用于 Tipsy Kernel Lite 那块屏幕和 Screen Lab 的 C6 接线。
目标是比较两种逐像素驱动策略的速度、对比度和残影，而非先移植完整产品功能。

## 硬件依据

Tipsy Kernel Lite 当前 platformio.ini 选择 `TIPSY_EPD_DRIVER_T94`，对应
GxEPD2_290_T94：GDEM029T94 / SSD1680，原生 128×296，横向 296×128。
这个判断来自已有工程配置，并非读取芯片 ID；若实物换过版本，需重新核对。
横向显示沿用原工程 rotation=3；通信采用 Screen Lab 接线，已经用户确认：

| 信号 | XIAO 标号 | GPIO |
| --- | --- | ---: |
| SCLK | D0 | 0 |
| MOSI | D1 | 1 |
| RST | D2 | 2 |
| DC | D3 | 21 |
| CS | D4 | 22 |
| BUSY，高电平忙 | D5 | 23 |

原生地址的 296 行使用完整 16 位地址，避免照搬 200×200 程序时第 256 行之后回绕。
没有使用 Tipsy 原来的 C3 GPIO 编号。

## 运行

在本仓库根目录：

```powershell
pio run
pio run -t upload
pio device monitor
```

上传会覆盖当前 C6 固件。多块串口设备同时连接时，为上传和监视命令加
`--upload-port COM数字` 或 `--port COM数字`，选择实际的 XIAO。
串口监视为 115200、回车发送命令。USB 原生串口重开不应重置设备。
上电先显示标准全刷参考图，保持高刷停止；发 `budget` 或 `net` 才进入高刷。

构建产物位于 .pio/build/ 对应环境目录；本仓库不附预编译固件。

| 串口命令 | 行为 |
| --- | --- |
| `apple` / `apple 12` | 播放完整无声 Bad Apple / 前 12 秒；开始时全刷，结束时完成剩余预算并关升压 |
| `budget` | 标准全刷、重置模型、运行默认预算策略 |
| `net` | 标准全刷、重置模型、运行累计净驱动限制策略 |
| `blocks` | 移动色块和圆点，观察大面积运动及静止背景 |
| `line` | 移动单像素细线，观察拖影和方向反转 |
| `reverse` | 同一区域黑 80ms、白 320ms，观察未完成转色时反向的差异 |
| `clock` | 显示百分之一秒计时；显示位数不代表光学响应精度 |
| `fps 15` / `fps 30` / `fps 0` | 目标扫描率；0 表示不限速，范围 0..60 |
| `spi 4` / `spi 10` / `spi 20` | MHz；先全刷并停止，再改总线速度，之后发 budget/net 恢复 |
| `end fast` / `end normal` | 全刷后选择 0x02 / 0x22 结束参数，用于单变量对照 |
| `window full` / `window partial` | 全刷后比较完整 RAM 写入与裁剪行写入；v3 默认 full |
| `prepare` | 全刷、等待 3 秒、只启用快刷波形和电源，不扫描像素；8 秒后自动关闭升压 |
| `hold N` | prepare 后执行 1..200 次全零掩码扫描，随后关闭升压并保留画面，不全刷 |
| `pulse 7 7` | 分别设置黑、白扫描次数或净驱动界限，范围 1..32；先全刷再生效 |
| `speed 24` | 色块和细线的像素/秒，范围 1..120；改变时全刷 |
| `settle` | 冻结当前目标，完成剩余预算和 HOLD 收尾后关闭升压；不做全刷 |
| `clean` | 标准全刷、清空历史，若原先运行则恢复 |
| `stop` | 全刷当前目标图并关闭模拟电源 |
| `status` / `help` | 状态和命令列表 |

切换策略或图案都会先全刷，保证比较起点一致。串口命令不能并发访问面板；
由同一个任务处理 SPI。默认 20MHz、目标 30Hz、24px/s、黑白预算各 7；没有 50MHz 超规格选项。

建议先 `budget` → `blocks` → `fps 15`，确认极性和移动方向，再测 `fps 30`
或 `fps 0`。保持同一 SPI 和图案，切到 `net` 比较。最后 `stop` 后看残影。
`reverse` 和 `line` 用于短时间比较，不是寿命验证。

## 两种策略的取舍

参考 SmoothEPD 主线的 epd_fast.c 与 epd_fast_net.c.bak，独立实现核心规划逻辑：

| | budget：显示效果优先 | net：限制净驱动 |
| --- | --- | --- |
| 新目标出现 | 重新给黑/白 7 次预算 | 向目标继续驱动，但累计差不能超出 -7..+7 |
| 中途反向 | 仍给新的完整预算，可能积累偏置 | 原方向用了多少，会影响允许的反向次数 |
| 完整反向的代价 | 通常 7 次扫描预算 | 从 -7 到 +7 可能需要 14 次扫描 |
| 显示取舍 | 往往对比度、运动表现较好 | 作者报告拖影更重；不等于“除残影增强版” |
| 维护 | 每 20 秒尝试同向小补偿 | 没有同样的小补偿步骤 |
| 标准全刷 | 每 45 秒或 2000 次扫描，先到为准 | 相同 |

两者有相同波形、SPI、7 次参数和测试画面。计数只是脉冲差模型，
不是电荷、粒子位置或反射率传感器。不能据此保证寿命。
为防快速非对称图案使历史回绕，这里用 int16_t 保存脉冲差；
与上游 int8_t 的实现有意不同。规划器约 128KB，另有图像、DMA 和运行库。

SmoothEPD README 原文：“实际测试下来这种方式可以支持非常长时间的快速刷新，
由于墨水粒子存在惯性，拖影很重。”这是作者对净驱动限制策略的观察，
不是对本板、本屏的实测。这里只验证算法取舍。

## 波形与正常全刷

正常全刷按已有 T94 驱动的参数使用面板 OTP 波形，更新控制为 0xF7，
不搬 1.54 寸屏的全刷表。快刷基于 Waveshare 2.9 V2 的
`_WF_PARTIAL_2IN9`：保留原表的电压及扫描频率参数，
把 00/11 改为 HOLD，缩短时间段，0x26/0x24 分别传黑白掩码，
0x0C 触发并保留模拟电源。v2 默认把结束参数单独覆盖为 SmoothEPD 的 0x02，
0x22 仍可对照；没有改动 VCOM 来凑速度。是实验改造，未获厂家对本实物的验证。
没有任何 OTP 写入或烧写波形指令。

快刷升压保持开启直到标准全刷或 stop，不能用普通低频墨水屏的休眠功耗估计。
超时或 SPI 失败会停止运行并锁定错误，模型不继续扣脉冲；重启后恢复标准参考。
若出现故障，仍应断电检查实际接线与面板状态，程序停止不代表物理面板已恢复。

## 应当怎样理解速度

2026-10-29 在这块 XIAO ESP32-C6 + T94 实物上对比，均为移动色块、80px/s、
黑白预算 7/7、不限速；每组两段 2 秒日志的均值（短测，不含标准全刷停顿）：

| 配置 | 扫描率 | BUSY |
| --- | ---: | ---: |
| v1、10MHz、结束参数 0x22 | 12.32Hz | 约 60ms |
| v2、10MHz、结束参数 0x22 | 14.52Hz | 约 60ms |
| v2、10MHz、结束参数 0x02 | 36.31Hz | 约 20ms |
| v2、20MHz、结束参数 0x02 | 39.55Hz | 约 20ms |
| v2 net、20MHz、结束参数 0x02 | 37.83Hz | 约 20ms |

因此前版 60ms 的主要原因已由结束参数单变量对照确认，不是面板的固有上限。
规划器跳过静止像素，减少约 8.4ms 至约 1ms；绘图与屏幕扫描重叠。
v2 每次只上传当前及上次非零掩码覆盖行的并集，清除旧掩码；第一次清完整 RAM。
后续发现静态文字变灰，v3 默认改为每次完整写两张 RAM 掩码，先核实真实芯片的窗口行为；
上述速度表属于 v2 partial，不能直接当作 v3 full 的成绩。window partial 可恢复裁剪写入对照。
逐像素预算在扫描完成后才提交，失败时不继续推进模型。

v5 在全刷切换快刷时补回上游要求的硬件复位并重新配置 T94 地址参数，部分路径不做软件复位。
诊断期间在全刷完成后额外等待 3 秒，便于区分全刷未结束与快刷准备阶段扰动。
普通动画的 clean/start 也保留这个等待；启动/定期全刷停顿因此加长，不包含在扫描率统计里。
30Hz 预设保留时序余量；`fps 0` 可探索最高扫描率，实际受图案活动范围影响。
默认速度从 80 降到 24px/s，16px 色块在一个位置驻留约 667ms，
给 7 次预算或净驱动反向更多完成时间。这不是经光学测量得到的最佳剂量；
残影和对比度仍需目视比较。四灰阶、流体模拟不在本固件内。

## Bad Apple 播放

完整片长 232.05 秒、4641 帧，内容按 20 帧/秒推进；原比例放进横向 296×128，
两侧留黑边，无声音。约 3.08MB 的压缩数据随固件保存在板载闪存中，播放时无需电脑传帧。
素材来源和重新转换方法见 assets/README.md；仅视频构建需要自行生成 assets/badapple.bin，并使用 xiao_esp32c6_video 环境。默认构建无需视频。
当前分区使用 4MB 闪存中的单个大应用区，没有第二个 OTA 应用槽。

串口发送 `apple` 即开始；`settle` 冻结收尾并保留画面，`stop` 全刷后停止，
`blocks` 返回方块和球测试。完整播放期间每 45 秒仍会全刷清理，视频时钟随之暂停，
每次停顿约 4.75 秒。保留 v5 的硬件复位修复、电压和 7/7 预算，没有提高驱动电压。

电脑监看脚本从本仓库根目录运行（Python 需 pyserial）：

```powershell
python tools/play_apple.py --port COM7 --seconds 12
python tools/play_apple.py --port COM7 --log .scratch/bad-apple/full-playback.json
```

脚本通过 --port 选择串口；第二条播放完整影片并保存串口记录。
脚本占用串口期间，可把 .scratch/bad-apple/control.json 改成 `{"stop":true}`，
它会请求冻结收尾、确认关闭驱动电源后退出。视频本身在板上执行。

20 帧/秒是目标图像推进速度，约 36 次/秒的驱动扫描也不代表每帧都已完全黑白转色。
快速转场可能在前一目标尚未完成预算时反向，实际残影和层次需要观察实屏。
12 秒实物短测已正常结束，扫描约 35～37 次/秒，最终 running=0、fault=0、analog=0。
初次转换的旋转方向写反；按用户反馈改为与 GFX rotation=3 一致的原生映射，
重新转换、校验并烧录后，用户确认方向正确，之前反馈人物轮廓清楚。
修正后的完整 232.05 秒内容已在实物播完，5 次定期全刷后均恢复播放，最终
running=0、fault=0、analog=0；保留末帧，没有额外全刷。
本次实机日志见 measurements/video-playback.json。

解码测试逐帧核对全部 4641 帧，并检查随机跳转、截断和错误偏移：

```powershell
g++ -std=c++17 -O2 -Wall -Wextra -Werror -Isrc tests/apple_test.cpp -o tests/apple_test.exe
./tests/apple_test.exe
```

每两秒输出 `MEASURE`：

- `scan_hz`：这段时间实际交给面板并完成的扫描率，包含补偿和 HOLD 扫描；
- `plan_us`：平均逐像素规划耗时，不含绘图；
- `upload_us`：平均两平面及其地址命令耗时；
- `busy_us`：BUSY 上升沿到下降沿的中断时间差；
- `render_us` / `commit_us`：平均绘图、提交已完成驱动历史的耗时；
- `overruns`：目标周期来不及完成的次数；
- `scans`：距上次标准全刷的扫描数；`heap`：当时剩余堆。

`scan_hz` 不是每个像素完全变色的速率；需要 7 次预算时，
30Hz 下完成预算约跨越 233ms 墙钟时间。中途反向和净限制会改变这个过程。
标准全刷耗时独立输出为 `CLEAN`，每两秒的扫描统计不含全刷停顿，
因此也不能把它当长期连续动画的平均帧率。

## 验证记录（2026-10-29）

- XIAO ESP32-C6 固件编译通过并已烧录；v2 静态 RAM 约 164KB，
  实际运行剩余堆约 283KB，具体见串口。
- 桌面 C++ 测试通过：7 次预算、未完成反向、净驱动界限、同向补偿、
  原生第 295 行、超过 8 位范围的历史记录、不提交就不扣驱动历史。
- 随机参考算法对照 480 帧通过，覆盖稀疏/密集变化、不对称预算、补偿、反向；
  部分 RAM 写入模拟覆盖掩码缩小、移位、清空与第 295 行，未留下旧驱动数据。
- 上述刷新时序是实测；尚无光学反射率或耐久测量，不用日志代替残影目视判断。
- 硬件回归脚本 tools/measure.py 每组结束均 stop 并确认 running=0、fault=0，
  已整理的原始日志见 measurements/。
- 默认 30Hz 预设实物连续检查稳定约 29.4Hz，无周期超时；已观察到 45 秒自动全刷。
  4/6 不对称预算和 settle 的完成预算、HOLD、关闭升压流程也已通过，最终恢复 7/7 并停止。
- 后续用户反馈：不限速下静态文字逐渐变灰，静态保持的光学效果尚未通过。
  收到反馈后已停止并标准全刷；没有把高扫描率视为显示质量验证完成。
  需要继续区分 HOLD/公共电极偏置/收尾、实际 RAM 映射与局部上传行为；
  500 扫描的静态 UI 掩码测试只验证软件不主动驱动参考区，不验证真实面板无漂移。
- v5 后续分阶段对照已定位并修复上述变浅：标准全刷单独停留时 UI 正常；
  v4 全刷后等待 3 秒，仅准备快刷、不进行像素扫描，用户仍观察到全部变浅。
  v5 唯一切换流程改动是补回原项目的硬件复位并重新配置 T94，然后才装载快刷波形；
  相同准备阶段保持黑色，约 12 秒、481 次全屏写入动画后静态 UI 也保持黑色，
  用户确认“问题消失了”。故本轮主要原因不是局部写 RAM 窗口或运动预算，
  而是全刷到快刷的切换流程遗漏。v5 full 实测约 38.5Hz；局部上传暂未恢复实物复验。
  3 秒诊断等待暂留，标准全刷停顿因此约 4.75 秒。
